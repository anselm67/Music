KernSheet via a shared Source protocol & Scorer fine-tune

Goal

Use the much more real KernSheet dataset (published / scanned piano scores with manually reviewed layout) to fine-tune the scorer end-to-end model, alongside the synthetic PDMX it trains on today.

Bottom line (revised): we are not morphing KernSheet's disk layout to look like PDMX. Instead we define a single Source protocol that yields exactly what staffer / noter / scorer need, and have both PDMX and KernSheet implement it. Datasets and models are abstracted from each dataset's on-disk layout. KernSheet stays exactly as it is on disk; the OMR editor keeps working untouched.

KernSheet layout JSON schema

pages:[ { page_number, image_width, image_height,
          staves:[ { rh_top, lh_bot, bars:[x,…] } ],   # one entry per grand-staff SYSTEM
          validated, image_rotation } ]
Key semantic: each KernSheet “staff” entry is really a grand-staff system — it stores only the outer envelope (rh_top, lh_bot) plus barline x-positions, not the inner treble/bass split and not absolute bar numbers.

Design — the Source protocol

Standardise on the existing Score hierarchy as the layout currency (all three datasets already consume Score.from_json). The protocol exposes Score directly — no new wrapper type. Datasets do their own page expansion exactly as they do now (for page in score.pages). 

class Source(Protocol):
    def scores(self) -> Iterable[Score]: ...                       # enumeration (layout included)
    def image(self, score: Score, page_number: int) -> Tensor: ... # raw page px; dataset transforms
    def records(self, score: Score, first_bar: int,
                last_bar: int) -> list[str] | None: ...            # tab-joined kern lines
  • scores() and image() already exist on PDMX in spirit (df enumeration + get_path("png")).
  • records() is the one genuinely new method — it wraps the KernReader.get_text currently inlined in the datasets. Returns tab-joined record lines; the dataset still splits per spine (text.split("\t")[spine]).
  • Vocab is out of the protocol — there is exactly one vocab, shared by all sources. It is built once and passed to each dataset alongside the source; PDMX and KernSheet both point at the same vocab.json.

Package layout

  • src/sheetmusic/ — the shared domain layer: the Source protocol and the Score hierarchy (Score / Page / System / Staff / Box, lifted out of src/pdmx/layout.py since it is dataset-agnostic). Name chosen to avoid the score/scorer collision.
  • src/pdmx/ — PDMX handling + PdmxSource, a thin adapter over the existing PDMX (keeps its builder/query role from bloating). Only net-new behaviour is records().
  • src/kernsheet/ — KernSheet handling + KernSheetSource (reads catalog.json + KernSheet's own files; where the real work lives, below). Eventually also the editor ported from OMR (cv2 HighGUI). On port, the heuristic OMR/staffer.py layout detector (projection/peak finding + deskew) is dropped — seed layouts from the trained Staffer model (stave-primary-grid-full) and let the human review/correct. We keep only its apply_page_transforms (pdf→png in annotation space), which KernSheetSource.image() reuses.

Nothing depends on a concrete dataset except through Source; both adapters depend on sheetmusic.

KernSheetSource responsibilities (the hard content work)

Invisible to the models — all behind the protocol:

  • Stave split (Decision B): synthesize per-stave boxes from the rh_top/lh_bot envelope when building each page's Score layout (midpoint now; re-detect lines later). Handle staff_count == 1 systems too.
  • Bar alignment: set first/last_bar_number per system by walking the kern's =N sequence in reading order, so records() returns the right measures.
  • Derived caching: pdf→png and krn→tokens cached wherever KernSheet likes (e.g. KernSheet/build/); the models never see it. PNG rasterisation must reproduce the annotation space — resize to width 1200 then rotate by image_rotation (port OMR/staffer.py:apply_page_transforms). Tokens via the Music kern.tokenize (now emitting numbered =N barlines).
  • Validation guard: assert Σ(annotated measures) == kern measure count; flag & exclude offenders (pickups, repeats, multirests). Never silently misalign.
Alignment is tractable. KernReader (src/kern/kern_reader.py) indexes tokens by the absolute =N numbers written in the kern, and get_text(first, last) slices between those markers — so we align annotated systems to the kern's own numbering rather than inventing numbers.

Phases

Phase 1 — Extract src/sheetmusic/

  • Move the Score hierarchy from src/pdmx/layout.py to src/sheetmusic/; add the Source protocol.
  • Update imports: pdmx internals (from .layout import) and the external sites (scorer/staffer/noter datasets, cli/staffer, verovio/scraper) to from sheetmusic import ….
  • uv run mypy src tests + uv run pytest green — pure refactor, no behaviour change.

Phase 2 — Refactor datasets onto Source + shared vocab

  • Datasets take a Source and a Vocab instead of a PDMX; replace inline get_path/KernReader calls with source.image() / source.records().
  • Add PdmxSource; wire the datamodules through it.
  • Verify PDMX scorer/staffer/noter training is byte-for-byte equivalent (same samples, same loss curve on a short run).

Phase 3 — Implement KernSheetSource

  • scores() from catalog.json (validated entries).
  • image() — pdf→png cache in the annotation space.
  • records() — over the regenerated numbered .tokens.
  • Layout build: envelope→stave split + =N bar alignment + validation guard, emitting Score objects.
  • Diagnostic: render a few stave crops with their assigned token sequences to confirm crop/token correspondence.

Phase 4 — Fine-tune the scorer

  • Start from the best checkpoint; reuse the shared vocab; report KernSheet OOV rate.
  • Held-out KernSheet val split by composer; keep a PDMX val slice to watch for catastrophic forgetting; lower LR / short warmup.
  • Tag train/… before launching; update docs/scorer-training.html after.

Main risk

Bar-number alignment is the chief correctness hazard: any system whose annotated measure count diverges from the kern's =N sequence (pickups, repeats, second endings, multirests) will misalign tokens to crops. Mitigation is the count-match guard in Phase 3 plus the crop/token spot-check.
