Cross-stave transcription: decode a system's staves in lockstep with a gated cross-stave attention sublayer

2026-06-16 · landed 2026-06-17 Accepted — production noter (NoterModel, NoterDataset) + scorer decode · supersedes the agreement reranker (_generate_rerank, now removed) · cf. the ceiling-decomposition entry below

Context

The ceiling-decomposition entry below pinned the real-scan limiter on transcription, not detection: staffer's system grouping is ~99% correct on KernSheet (the constraint-layer diagnostic: 5681 pred vs 5670 GT staves, 5 miscounts, 2789/2816 systems clean), so detection is not the ceiling. The ceiling is the 78% of systems whose independently-decoded spines disagree on the barline grid. Two of the named levers point the same way: the .-continuation grid is worth ~+2.4pp (how many continuations a staff emits is set by when the other staff has events — a per-stave decoder cannot know it), and the runaway / early-EOS tail is a length-disagreement between siblings. The agreement reranker (_generate_rerank) already attacks this, but only post-hoc: it reranks independently-decoded beams toward cross-staff barline agreement. It cannot inject information a stave never decoded.

The enabling fact is in the data. A .tokens file is a row-aligned spine grid: each row is one musical timestep, tab-separated cells are the spines, the . null tokens exist precisely to keep every spine on the same row, and a barline (=N) lands at an identical row index across all spines. Length and EOS row are shared too. A scan of all 674 multi-spine KernSheet files found 1 ragged file (0.1%, a mid-piece spine split that the existing per-sample skip already drops) and 0 barline-skewed rows — real-scan kern is as cleanly aligned as Verovio-canonical PDMX. And because the layout JSON carries one bar range per system, a per-stave bar mismatch is structurally inexpressible. So synchronized cross-stave decoding has honest, aligned labels by construction.

Decision

Make the transcription unit a system (its G staves) instead of a single stave, and couple the staves in the decoder. The whole change lives in noter; scorer inherits it because it embeds a NoterModel.

  • Sample unit. NoterDataset.items becomes per-system: each item yields G stave crops + G row-aligned token sequences (same T, same EOS row — they already are in the file), padded to max_staves with a stave-mask. G-general, so it is also a free step toward >2-staff systems.
  • Gated cross-stave attention sublayer. Keep the noter decoder layer's three existing ops (causal self-attention over time, cross-attention to the staff's own image memory, FFN) and add a 4th: every stave attends to the other staves of its system along the row axis under the same causal mask (stave i, row t sees stave j, rows ≤ t). Hidden state per system is (G, T, D). The sublayer's output projection is zero-initialised, so at init the model is bit-identical to the production noter and single-stave systems stay identical forever.
  • Lockstep decode. Generate row t for all G staves simultaneously; each stave sees its siblings' rows < t, so "my sibling just put a barline here" is an input, not a post-hoc vote. Agreement becomes structural; the --rerank reranker becomes redundant (kept only as optional belt-and-suspenders).
  • Scorer. The crop bridge is untouched — it still cuts individual stave crops. Scorer groups them by the system index it already computes (sys_ids at train, owners at inference) and calls noter's system-level decode instead of a flat K-batch. Both standalone checkpoints still transfer wholesale.

Rationale

The gated additive sublayer is chosen over two alternatives. A single interleaved sequence (concatenate all staves per row) kills disagreement by construction but cannot warm-start from the production noter and forces a giant G·max_chords·V head. Encoder-side coupling (letting crops see each other) does not address what is a decoder/temporal problem. The gated decoder sublayer is the one design that is both principled and reuses the production checkpoint — the same additive-bridge philosophy the scorer already uses for the crop bridge. It targets the decomposition's named failure modes directly: the .-grid (a stave now knows when to emit a null to stay aligned), runaway / early-EOS (siblings pull a diverging length back), and leaves only the ~4.6% shared-wrong-timeline floor it structurally cannot beat.

Status / outcome

Landed and promoted to production (lineage bruckner, 2026-06-17), built exactly in the planned order: dataset restructure + system-collate → CrossStaveDecoderLayer (noter dropped nn.Transformer for split named encoder/decoder) → standalone noter warm-started from mahler's noter → rehearsal-mix fine-tune (bruckner-mixed) → scorer re-merge. The --rerank reranker and the beam apparatus it rode on were removed, not kept as belt-and-suspenders: agreement is structural in the lockstep decode and greedy already wins.

Every controlled comparison (same recipe / =|| vocab / rehearsal mix, warm-started from the same mahler checkpoint — cross-stave attention the only variable) is a win:

  • Standalone noter (bruckner-mixed), free-running: PDMX 95.7 → 97.5% (+1.8), KernSheet 89.4 → 95.5% (+6.1) vs mahler-mixed — the gain concentrated on real scans, as predicted.
  • End-to-end scorer (bruckner), eval --size 500 --seed 0: KernSheet 91.0 → 95.0% (+4.0), PDMX 96.1 → 97.7% (+1.6) — and bruckner's figures are greedy lockstep, beating mahler's beam-8 + rerank best with a simpler, cheaper decode.

The one regression is PDMX stave-counting (scorer miscount 5 → 9 / 500), small and on the already-saturated clean domain; KernSheet counting improved (9 → 7 / 500). Net: the success criterion is met — the .-grid gap closes and the desync population's joint-correctness is recovered in-decode rather than by a post-hoc vote. bruckner supersedes mahler as the production end-to-end model.

Why KernSheet end-to-end is stuck at ~91% — it's a transcription ceiling, not a detection one — mahler-ks

2026-06-16 Not promoted scripts/scorer_ceiling_probe.py · run mahler-ks · cf. the ScanAugment & rehearsal-mix entries

Context

A recurring frustration: KernSheet end-to-end similarity sits near 91% no matter the intervention — ScanAugment (a clean detector win), letterboxing, and now mahler-ks, a fine-tune off 128 hand-corrected staff_height scores whose boxes were visibly "all over the place". mahler-ks vs mahler on the same current (edited) KS data: 90.9% vs 90.8% (rerank 91.4 vs 91.3), miscount 14 vs 11 — a wash. The data is genuinely cleaner and that is banked; it simply doesn't show up here. Rather than run another model, we instrumented the eval to ask why nothing moves it.

What we found

The eval metric matches staves by center-y and then scores token similarity on the matched staves — detection quality shows up separately as miscount. So the 91% is a transcription number sitting downstream of detection: augment, box cleaning, and letterboxing are all detector-side and structurally cannot move it. The crop the noter receives was already good enough.

Decomposing 300 pages / 3401 matched staves (scorer_ceiling_probe.py):

  • raw mean 91.0%, but median 94.3% — a tail, not a uniform error;
  • .-stripped mean 93.4% → a cross-stave/system joint decode is worth ~+2.4pp. The . continuation tokens encode a shared system time-grid (how many continuations a staff emits is set by when the other staff has events), which a per-stave decoder cannot know — so . counts drift both ways;
  • U-shaped in length: 30–60-token staves score 92% and are 90% of the data; both extremes are worse;
  • the <80% tail (11% of staves) splits 76% note-divergence (right length, wrong notes), 17% runaway-repeat (decoder loops into a rest/8/. wall), 7% early-EOS (truncates — a real un-length-normalized beam bias in _beam_some).

The reading

"Stuck at 91%" is really "a high median with an 11% tail." The levers are now concrete and none are detector work: (1) the dominant tail — note-divergence — is unadjudicated and splits the future: genuine model misreads (a model/training lever) vs edition mismatch between the scanned IMSLP edition and the Humdrum .krn (an irreducible label ceiling, fixed only by curating/excluding bad-edition pages); (2) decode-time safeguards (length-normalization for early-EOS, a max-consecutive-repeat cap for runaways) recover ~1–1.5pp with no retraining, applied surgically since music repeats legitimately; (3) a system-level joint decode recovers the ~2.4pp .-grid. mahler stays production. Next step is eyeballing the 55–80% note-divergence band against the scans to settle (1).

Scan-look augmentation helps the detector and nothing downstream — augment no good

2026-06-15 Rejected src/sheetmusic/transform.py (ScanAugment, commit 97849e1) · run mahler-augment · cf. rehearsal mixing & the photometric-gap entry

Context

The standing real-scan strategy is per-image normalisation plus a KernSheet rehearsal mix. Per-image norm is only an affine, though — it can rescale tone but can't synthesise the morphology of a scan (fattened ink, optical blur, paper texture, JPEG ringing). The hypothesis: a geometry-preserving print→scan augmentation on the crisp Verovio renders would teach real-scan appearance the affine can't, narrowing the PDMX↔KernSheet gap that the pixel histograms make visible. ScanAugment implements exactly that chain (ink spread, blur, paper tone + uneven illumination, sensor noise, JPEG), calibrated so augmented-PDMX stroke-width mean matches KernSheet (223 vs 221). It was wired behind a --augment flag and turned on at prob=0.5 for the PDMX bases only (the KernSheet fine-tunes already see real scans), and the whole mahler pipeline was rerun as mahler-augment on the same =|| vocab — a clean A/B.

What we found

Where augmentation is measured directly, it works: the standalone staffer real-scan boxes tighten 3.31 → 3.11 px (sys IoU 0.936 → 0.940) and the standalone noter KernSheet similarity ticks up. But the end-to-end scorer — the metric that ships — does not move: KernSheet similarity is 90.7% vs mahler's 91.0% (and 90.4 vs 90.6 without rerank), i.e. flat-to-slightly-worse inside the eval wobble. And it brings a PDMX tax: conceding clean-PDMX base accuracy (0.48 → 0.58 px) weakens objectness/count enough to roughly double PDMX miscounts (5 → 12 / 500).

The reading

Detection geometry was not the real-scan bottleneck. The boxes were already good enough that tightening them buys nothing for the transcriber sitting downstream; the limiter on real scans is the noter's reading, which crisper crops don't fix. So a genuine detector-level improvement produces a net wash-to-negative end-to-end, plus a counting regression on the synthetic domain. Decision: not promoted — mahler stays as production. Two lessons carry forward: the real-scan gap lives in transcription, not detection, so future augmentation energy belongs on the noter path rather than the staffer; and prob=0.5 on the staffer base was too strong for PDMX counting. The code stays behind its default-off flag for that future noter-side trial.

Page state grows from a validated bool to a status enum, and gets a reviews framework

2026-06-12 Accepted src/kernsheet/reviews.py · scripts/migrate_status.py · cf. the stave-height probe below

Context

A KernSheet page carried a single validated: bool — in the training feed when True, excluded when False. That one bit conflated two different things: "not yet reviewed" (fresh kernsheet detect output) and "reviewed and deliberately excluded" (an unfixable scan). And it offered nowhere to record the outcome of an automated check. The stave-height probe (entry below) had closed by proposing exactly such a check: a height-consistency QA pass in the editor that flags pages whose stave heights disperse beyond the annotation-noise floor. To host that, the page state had to get richer first.

Decision

Two coupled changes.

  • State. Page.validated: bool → Page.status: Status (PENDING / VALIDATED / REJECTED), plus Page.reviewed: list[str] — the names of automated reviews a human has acknowledged ("ok") on that page. Training/eval still feed on status == VALIDATED (a read-only validated property preserves every filter call site). Both corpora were migrated on disk in lock-step with the code — PDMX ~253k layouts (all validated) and KernSheet 627 (true→validated, false→pending) — via scripts/migrate_status.py, so there is no read-compat shim; the code speaks only the new schema.
  • Reviews. A registry of cheap geometry checks over a Score (kernsheet/reviews.py), each yielding page-level Findings. The first is staff_height: it flags a page whose within-page stave-height spread exceeds STAFF_HEIGHT_TOLERANCE_PX = 8 px — set just above the ~3.5 px KernSheet annotation-jitter floor the probe measured. Surfaced by kernsheet review (read-only report) and kernsheet edit --review staff_height (a worklist that opens the editor on each flagged page). In the editor: v cycles the status, o acknowledges the page's firing reviews into reviewed, and "fix" is just normal editing — the finding clears on the next recompute.

Rationale — recompute, don't persist

Findings are recomputed on demand, never stored. Each check reads only Score geometry already in the layout JSON — no images, no model — so scanning the whole corpus is a sub-second pass, and a finding can never go stale against a layout that was edited underneath it. The only thing persisted is the human's verdict: the status and the small reviewed acknowledgement set. A genuine fix needs no marker at all — once the geometry is corrected the check simply stops firing. This keeps the on-disk schema minimal and the framework trivially extensible: bar-count mismatch, bar-number continuity and staff-count consistency are all one-line @register additions over the same Score.

Outcome. At 8 px, staff_height flags 287 pages across 161 scores (11% of 2,625 KernSheet pages) — median within-page spread is 3 px (p90/p95/p99 = 9/11/17 px), so the threshold sits cleanly above the label-noise floor and surfaces the real tail. The check is both a QA pass over existing GT and the instrument that separates the probe's open question — annotation jitter vs. real scan skew — page by page, as a human walks the worklist and chooses ok / fix / reject.

The stave-height invariant is exact in PDMX but loose in KernSheet — and the slack looks like GT noise

2026-06-11 Finding throwaway GT probe · cf. staffer-training

Context

A standing idea for the staffer: every staff on a printed page is engraved at one rastral size, so stave heights within a page should be constant — an unused structural prior we could lean on (a soft height-consistency loss, or even bottom = top + shared_height). Before building anything, the honest first move is to check the premise in the ground truth itself. A throwaway script measured the within-page coefficient of variation (CV = std/mean, scale-free) of stave heights (box.bottom − box.top) on ~400 sampled scores from each of PDMX and KernSheet.

PDMX: the invariant is exact. Stave-height CV is 0.00% from median through p99; 99.2% of multi-staff pages sit under a 2% CV (4,869 staves, 646 pages). Verovio renders every staff identically — within a page the heights are pixel-for-pixel equal.

The uncomfortable reading

On KernSheet the invariant is only approximately true: the median within-page spread is 7.8% ≈ 3.5 px on a 45 px staff, with a real tail (p99 spread ~30%, ~13 px). The discomfort is the magnitude — that ~3.5 px is the same order as the ~3.5 px stave error the model posts on KernSheet. Two facts make the likely cause GT imprecision, not the model: (1) the rastral size on a flatbed-scanned printed score is physically constant, so genuine height variation should be ≈0; (2) the KernSheet boxes are hand-placed/manually-validated, and the spread we see is exactly what pixel-level annotation jitter produces. So part of what we've been charging to the detector on KernSheet may in fact be noise baked into the labels — the GT is less precise than it was assumed to be.

A secondary structural note fell out of the same probe: even in PDMX, system heights vary among systems sharing a staff_count (p99 CV 10%) — the variation lives in the inter-staff gaps, not the staves. So the invariant is a stave property only; any prior must target stave heights, never system heights.

Consequences

  • A KernSheet stave-error floor. If the labels carry ~3.5 px of height jitter, sub-~3 px stave-error numbers on KernSheet should be read with suspicion — at that scale we may be measuring annotation noise, not model error. The PDMX numbers stay trustworthy.
  • Hard height-coupling is off the table — it would be perfect for PDMX but would fight whatever real (or noisy) variation KernSheet carries. A soft consistency regulariser remains viable and could double as a label denoiser (pulling outlier box heights toward the page mean), if the spread is annotation noise rather than true scan skew.
  • Open question this probe can't settle: real scan geometry (skew, perspective) vs. annotation jitter. On flat printed scans the balance tilts toward annotation, but it's unconfirmed. A cheap follow-up: a height-consistency check in the KernSheet editor that flags pages whose stave heights disperse beyond a few percent — both a QA pass on the existing GT and the experiment that separates the two causes.

Rehearsal mixing: PDMX as a secondary stream in every KernSheet fine-tune

2026-06-11 Accepted ccbca9a · tag train/debussy-mixed · src/sheetmusic/mixed_source.py

Context

Fine-tuning a PDMX-trained model on the small (~2.3k-page) KernSheet corpus buys real-scan accuracy but catastrophically forgets PDMX. The KS-only fine-tune (debussy-kernsheet) measurably erodes what 500k synthetic pages taught: the noter drops from ~97.8% to 93.6% PDMX free-running, and the staffer nearly doubles its PDMX stave error, 0.90 → 1.73 px — and the damage is broad, not confined to the rare deep-page slots (bin 0 bottom-edge error jumps 0.2 → 2.7 px). The forgotten regions are exactly the low-frequency tail that drags an eval average. This matters end-to-end: the same erosion hits all three fine-tune sites — staffer, noter, and the scorer joint fine-tune.

Decision

Rehearsal. Mix PDMX back into the fine-tune stream so the network keeps practising the synthetic domain while it learns the real one. One new flag — --kern-sheet <ROOT> <MIX> — on all three train commands; MIX ∈ (0,1) is KernSheet's share of each epoch. PDMX stays the primary corpus from the global options; KernSheet is the thing injected. Omitting the flag is byte-identical to before (it is the only new branch).

Rationale — why at the Source layer, and why PDMX-primary

The first cut mixed at the dataset layer (a weighted child-pick MixedDataset that also had to re-fold the staffer bottom-bias sample weights). Reverted. Mixing belongs at the Source layer — the read-only scores()/image()/records() protocol the datasets sit on — because then the entire downstream pipeline is reused untouched: the random_split, the noter box-jitter view, and crucially the staffer bottom-bias WeightedRandomSampler, which now naturally rehearses PDMX deep pages for free. A composite source can still hold a target ratio: MixedSource walks the primary once and injects the secondary (cycled/oversampled) against a running ratio target, rather than a naive scores() concatenation. Score ids are namespaced 0::id / 1::id so the id-keyed methods route back to the owning child. The convenience entry point is PdmxSource.mix(secondary, fraction) → MixedSource, since the path is always PDMX → mixed.

Mix semantics that mooted an epoch-count question. Epoch size stays train_len; the split is MIX·train_len KernSheet + (1−MIX)·train_len PDMX. So steps/epoch are unchanged and the mix fraction alone carries the KernSheet exposure — an earlier "fine-tune for ×1.5 the epochs" idea fell away. The ratio is exact at score granularity and approximate at the item (staff/bar-range) level, since pages differ in samples-per-score across domains — an acceptable wobble.

Result — staffer debussy-mixed (67% KernSheet) validates the design. PDMX competence is largely restored: 1.73 → 1.22 px, recovering ~61% of the loss the KS-only fine-tune incurred, at a small bounded tax over the pristine base (+0.32 px, concentrated in the deep bins that no longer get full attention). And it costs nothing on the target domain — KernSheet error actually improves 3.83 → 3.55 px, likely the regularising effect of the larger, more varied stream. One model now does both domains with no catastrophic forgetting.

So rehearsal is not a KernSheet-vs-PDMX trade-off here — it is a strict improvement over the KS-only fine-tune that also recovers most of the forgotten synthetic competence. The same --kern-sheet path now rolls out across the pipeline: the noter mixed fine-tune (debussy-mixed, 67% KernSheet) reproduces the result — PDMX free-running recovers 93.4 → 96.8% while KernSheet holds flat (90.7 → 90.9%), the same close-the-forgetting-at-no-target-cost shape the staffer showed (see the noter card). The scorer joint fine-tune (third forgetting site, detector unfrozen) follows on the same flag. Caveat banked: KernSheet is genuinely harder, so rehearsal narrows the gap rather than erasing it — the forgetting/overfit component is what it removes.

torch.compile on the training forward — added, measured, reverted

2026-06-10 Reverted aa617e9 (add) · f9d8e81 (revert)

Context

An opt-in --compile/--no-compile flag was added to all three train commands (staffer/noter/scorer), torch.compile-ing only the training forward path while inference stayed eager. The wiring itself was clean: a keep-original pattern stored the compiled callable off-module via object.__setattr__ so state_dict kept no _orig_mod. prefix and checkpoints loaded strict in both directions.

Decision

Reverted. The mechanism worked; the speed didn't. The bar for keeping torch.compile is not "it compiles cleanly and the checkpoints interop" — it's "it makes training faster." It did the opposite.

Result — staffer training was slower compiled. ~3.0 it/s with --compile vs ~3.6 it/s eager — a persistent ~17% regression, measured in steady state (not warmup, which would only cost the first few steps). A loss that survives past warmup means compile is doing actively worse work every step.

Why it lost here

  • Wrong regime. torch.compile pays off on large, compute-bound, fixed-shape models. Staffer is a small D=256 ViT detector on a 4060/5060 Ti — closer to launch-/memory-bound, where default-mode fusion buys little.
  • Shape variance is the likely killer. Staffer trains on full page images; if dimensions vary batch-to-batch, Dynamo either recompiles per shape or falls into dynamic-shape mode — guard overhead every step and less-fused kernels. Diagnose with TORCH_LOGS=recompiles.

Not a fundamental dead end — it was never A/B'd on noter, whose fixed (64×768) crops are exactly the no-shape-variance regime compile likes. If revisited, start there, and try mode="reduce-overhead" (CUDA graphs claw back launch overhead on small models) only once shapes are confirmed static. The lesson banked: a perf feature that doesn't measurably improve perf is dead weight, however cleanly it's engineered.

A system-level constraint layer over the scorer: cross-staff barline-position agreement

2026-06-10 Exploring scripts/scorer_system_agreement.py · debussy scorer

Context

The scorer decodes each staff of a system independently, so its spines can drift out of structural agreement (the classic autoregressive desync — a dropped or doubled event slips every later token, cf. the .-token entry below). The idea: a step at the system level that reranks the joint beam combination of a system's staves toward mutual structural consistency. Within a system every spine shares the barline skeleton, so barline positions are a cross-staff invariant — the natural first constraint.

Decision & method

Start with reranking, not constrained decoding or repair, and measure it on the right unit and the right model. Two throwaway noter-level scripts (a per-stave bar-count recall probe and a per-system GT-box agreement probe) were written and then dropped: both wired noter to GT crops and grouped staves by a GT bar-range key — exactly the structure predicted boxes perturb. The debussy scorer is already the end-to-end predicted-box pipeline (detect → crop → transcribe), and its predict() returns owners — the detected system index per stave — so it hands us the honest, detection-derived grouping for free. scripts/scorer_system_agreement.py runs it and, per predicted system, measures:

  1. Disagreement rate — how often a system's staves disagree on barline positions at the beam-0 (argmax) decode; staff-vs-staff, no GT, the rerank's target set.
  2. Consistency ceiling — does a signature present in every stave's candidate set exist (a mutually-consistent combo reachable in the beams)? Also GT-free.
  3. Correctness & the agreement↔correctness gap — on systems whose staves cleanly match GT staves (center-y Hungarian, no miss/extra): is GT reachable, and is the logprob-best consistent combo actually GT? A low gap ⇒ staves agree on a shared error — the key risk for an agreement-only objective.

Signature = the set of timestep indices carrying a = (both spines share one record-row timeline, so a barline lands on the same row in each). It is brittle by design: a single early .-insertion shifts every later index, so "disagreement" mixes genuine structural desync with benign off-by-one shifts. Code prerequisite, shared with the reranker: ScorerModule._beam_single returns only beam[0], so the script carries a beam_all that surfaces all candidates + cumulative slot-0 logprobs.

Result — debussy scorer, 500 KernSheet pages, beam 16. Detection is a non-factor (5681 predicted / 5670 GT staves, 5 miscount pages, 2789/2816 systems cleanly GT-aligned) — so this is almost purely a transcription-desync signal. The system count partitions exactly: agree + disagree, and within the clean subset correct + agree-but-wrong + disagree.

Two ceilings cap it. (1) Of the 2187 disagreeing systems only ~1019 (46.6%) have any consistent combo in beam-16 — the rest need a wider beam, localized repair, or cross-spine coupling during decode. (2) Even a perfect agreement-reranker tops out at 38.9% exact joint-correctness; the other ~61% are unreachable by reranking alone. The now-dropped per-stave noter probe gave a comparable bound (clean GT-box val: recall ceiling 16.7%@8 → 29.5%@16 → 42.9%@32). No rerank code committed yet.

Beam search over slot 0 in scorer inference

2026-06-05 Accepted 5022327

Context

The scorer's predict() decoded autoregressively with plain greedy argmax. A recurring error pattern surfaced: the . token (Humdrum null record — "no new event in this spine at this timepoint," used to keep two spines in rhythmic alignment) was inserted or deleted spuriously. Because . is an insertion/deletion, not a substitution, a single wrong . shifts every subsequent token one position, cascading into many apparent mismatches and contributing to miscount (wrong stave length). Post-hoc error analysis on ravel: substitutions 61% of errors, structural ins/del 38.9%, 7.5% of systems desynced — and . insertions were the dominant ins/del class.

Generating . correctly requires knowing the other spine's current rhythmic duration — cross-spine state the decoder must maintain implicitly. Greedy commits immediately with no chance to recover once the wrong branch is taken.

Decision

Replace greedy with beam search (width 4) over slot 0 only (the primary token that governs sequence structure, including .); chord slots 1–7 remain greedy from the selected beam's logits. Staves are decoded one at a time rather than in a single K×B batch, so peak memory scales with beam width, not K×beam width (the batched version OOMed at B=4 on a 16 GB GPU with a dense page). The original greedy path is preserved via predict(use_beam=False).

Why beam over slot 0 only?

Slot 0 is the structural decision: note vs ., note vs EOS — these determine sequence length and alignment. Slots 1–7 are chord tones, independent per slot, and secondary to the structural choice. Beaming over the full chord (vocab8) is intractable; beaming over slot 0 targets exactly the failure mode.

Why not constrained decoding?

Constrained decoding would fix the . problem structurally — only allow . when the rhythm tracker says the current beat position is subdivided by the other spine. But it requires a Kern-aware beat-position state machine alongside the decoder. Beam search is a far cheaper first step; if it closes the gap, constrained decoding can stay deferred.

Outcome. 300-page KernSheet eval on ravel: avg similarity 89.6% → 91.3% (+1.7%), miscounts 9 → 5 (−44%). The miscount drop is consistent with beam search recovering from spurious . insertions, which shift sequence length. ~3× slower per-page (stave-by-stave loop vs batched greedy), acceptable for inference. Beam width 4 was chosen and not swept; a width sweep may show diminishing returns.

KernSheet via a shared Source protocol, and the KernSheet fine-tunes

2026-06-02 → 06-04 Accepted 68c663b · 2c76e75 · train/enhanced3-kernsheet · train/{boulez,walton,ravel}

Context

The models trained only on synthetic PDMX. KernSheet is the real corpus — published / scanned piano scores with manually-reviewed layout — and the natural fine-tune target. But its on-disk layout was a legacy "envelope" schema (one entry per grand-staff system storing only rh_top / lh_bot, plus barline x-coords; no treble/bass split, no absolute bar numbers), incompatible with the PDMX Score hierarchy the datasets consume.

Decision

  • One Source protocol abstracts both datasets behind four methods — scores(), score(id), image(id, page), records(id, first_bar, last_bar) — so staffer / noter / scorer never see either dataset's disk layout. Vocab is out of the protocol: one shared vocab.json passed alongside. Protocol + Score hierarchy live in a new src/sheetmusic/ (named to avoid the score/scorer collision); adapters PdmxSource / KernSheetSource live in their own packages.
  • Migrate, don't translate. A one-time script rewrote all 581 annotated KernSheet scores from the envelope schema into native Score JSON at KernSheet/layout/<id>.json (non-destructive; .krn/.pdf untouched). KernSheetSource.score(id) then just Score.from_jsons it — no per-load translation.
  • Stave split = thirds. Piano grand staff is always RH treble + LH bass: with delta=(lh_bot−rh_top)//3, RH = top third, LH = bottom third, middle third = inter-staff gap. Persisted at migration.
  • Shared vocab by extension. The frozen PDMX vocab (4784) was extended (not rebuilt — rebuilding reorders ids and invalidates the checkpoint's embedding/head rows) with KernSheet tokens at count≥2 → 5543 tokens; PDMX ids preserved, new tokens appended at the tail. Checkpoints grown with noter grow-checkpoint (handles the slot-major output head).
  • Drop the heuristic detector. The ported OMR editor keeps the book-keeping but its find_bars is a stub — layouts are seeded from the trained staffer and human-reviewed, not projection-peak heuristics.

Rationale

Migrating once keeps the load path trivial and makes Score KernSheet's native format (a step toward subsuming OMR entirely). The thirds split is a loose-but- correct approximation that lets us train immediately; crucially it means KernSheet boxes already carry ~15–25px inner-edge slop, which is why box-jitter augmentation is applied only to PDMX (tight Verovio boxes), not to the already-loose KernSheet fine-tune. Extending rather than rebuilding the vocab is what makes warm-starting from PDMX checkpoints possible at all.

Chief hazard — bar-number alignment. Any system whose annotated measure count diverges from the kern's =N sequence (pickups, repeats, second endings, multirests) misaligns tokens to crops. Mitigation: a count-match guard in migration (~31 scores excluded, flagged per-id not silently dropped) + crop/token spot-checks.
Outcome. Phases 1–3 (extract sheetmusic, refactor datasets onto Source, implement KernSheetSource + port editor) landed sample-for-sample equivalent on PDMX. Noter fine-tune enhanced3-kernsheet → 96.78% val token-acc (later beaten by the centering+jitter retrain at 97.41%). Scorer fine-tunes, composer-named worst-first: walton (frozen-staffer, 87.2%) < boulez (joint, 89.5%) < ravel (joint, 20 epochs, 90.7% sim / 3 miscount — current best). The monotonic gain came entirely from more joint detection training. Detail in scorer-training.html / noter-training.html.

Scorer end-to-end: a differentiable crop bridge, not a shared backbone

2026-06-02 Accepted 289cdce · cc4d374 · d0ee8ac · bbbc337 · train/merge1

Context

The goal of "end-to-end" is to let the transcription loss reach the detector, so it places boxes that transcribe well, not merely boxes with high IoU. The first instinct was to fuse staffer and noter onto one shared low-level feature map. This section traces the decisions — moved here from architecture.html §6/§8 — that led to rejecting that fusion in favour of a differentiable crop.

Starting point: naïve RoIAlign from the 16×16 backbone

Reuse the staffer's 16×16-patch ViT feature map (B, 256, 60, 43) as the RoIAlign source, output_size=(4, 192).

Problem: a stave is only 2–4 feature rows tall at 16px/patch — far too coarse for transcription, where vertical position encodes pitch.

Attempt: full 4×4-patch backbone

4×4 patches on the full page → 240×172 = 41 280 positions. A ViT on that many tokens is ~256× the attention cost of today's 2 580-token model.

Rejected on compute. But fine-grained features stayed the right idea.

Constraint surfaced: noter patch is (64, 4)

patch_width=4, patch_height=64 → Conv2d(k=(64,4)), 192 patches/staff. Pitch is encoded vertically in the 64px height; shortening it breaks the inductive bias and invalidates the pre-trained weights.

Considered: shared 4×4 embed + branch convs

One Conv2d(1→256, k=4) feeding both, per-branch convs restoring each patch granularity.

Rejected (deferred). Saves ~4K params; discards the noter's pre-trained encoder and forces the staffer ViT to re-adapt to two stacked random convs. Matching receptive fields ≠ matching the feature distribution the pre-trained stacks learned to read.

Decision

Keep both models intact; bridge them with a differentiable crop. The coarse-RoI problem only existed because we insisted on a shared source — cropping from the raw page dissolves it, and the noter samples at full pixel resolution exactly as standalone. The actual prize (transcription gradients reaching the detector) comes from the crop being differentiable in the box position, not from sharing anything.

Implementation caveat (verified): the crop must use affine_grid + grid_sample, not torchvision.ops.roi_align — the latter does not backprop to box coordinates (boxes.grad is None), carrying no gradient to the detector. The bridge reproduces the standalone noter crop exactly — a 1:1, left-aligned, right-masked 64×768 slice anchored at (top − h, left) — only differentiably. Both stage-1/stage-2 checkpoints transfer with no surgery.

Deferred sub-decision: shared patch embedding

Sharing the low-level embedding is Deferred, not adopted: it buys nothing measurable (≈4K params, one cheap conv — irrelevant next to the ViT and the AR decoder, and to the phone target) while imposing the most fragile weight transfer in the design. Revisit only if: profiling shows the duplicated conv is a real cost on-device (unlikely — both embeddings are tiny); evidence of low-level feature data-starvation appears (none today); or a redesign rewrites the low-level stack anyway. If revisited, keep the noter encoder (run it on the crops) rather than discarding it.

Outcome. The pre-merge diagnostic measured only ~0.86% transcription degradation feeding predicted (vs GT) crops to the unchanged noter — so the merge starts from a near-working pipeline and merely adds the gradient path. train/merge1 completed end-to-end; the package + CLI landed on main. The decoupled bridge later enabled the KernSheet scorer fine-tunes (see the entry above). Architecture detail in architecture.html §3–§5.

Staffer: per-edge LTRB boxes, then stave-primary grid anchors

2026-05-29 → 06-01 Accepted train/enhanced2-ltrb-anchor · train/stave-primary-grid · train/stave-primary-grid-full

Context

The standing defect was bottom-of-page drift: stave/system edges near the page bottom were off by ~12–16px while the top was accurate to ~1px. Two successive decisions chased it.

Decision 1 — direct LTRB system boxes (replacing cx/cy/w/h)

Predict each box as (left, top, right, bottom) directly, instead of (cx, cy, w, h). Under the old form bottom = cy + h/2 had no independent gradient — a cy bias toward the visually-dominant treble plus an underestimated h cancel at the top but compound at the bottom (the observed 0.9px-top / 16px-bottom asymmetry). LTRB gives every edge its own gradient. Rejected the earlier "chaining" idea (top[i+1]=bottom[i]) — saves 1 number in 8 for N=2 systems, not worth the error-propagation risk; the model learns structural coupling from data.

Decision 2 — invert the hierarchy + uniform grid anchors

LTRB helped but didn't flatten the drift. The deeper fix, stave-primary: invert staffer's hierarchy so staves lead and systems are derived (the system box has zero independent DOF — it's the hull of its staves, so a separate sys_box_head only let the copies disagree). Then freeze the stave anchors to a uniform grid (i+0.5)/M and route each GT stave to its nearest anchor (free, non-contiguous assignment). This trains every query at ~uniform frequency on a count-independent spatial band, so the rarely-fired high slots — the last source of drift — finally learn their position.

Rejected along the way (negative results, logged in staffer-training.html): iterative box refinement (anchor-iter, DAB-DETR style) was worse on every metric including the bottom bin; count-conditional anchoring was insufficient (it only encodes count-averaged position); bottom-bias sampler + 4× data didn't help, confirming the cause was structural, not data-starvation. vflip augmentation hurt top accuracy.
Outcome. stave-primary-grid-full (D=256) is the PDMX best: sys IoU 0.985, stave edge error 0.41px, bottom drift collapsed from ~12–16px to ~1px. This is the detector feeding the scorer; it was later KernSheet-fine-tuned (stave-primary-grid-full-kernsheet), halving the real-scan domain gap (top 7.4→3.2px, bot 6.3→3.1px). Per-model metrics in staffer-training.html.
